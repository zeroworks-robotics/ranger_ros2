# Ranger Mini 3.0 드라이버 — 상태 관측 수정 정리

2026-09-14. `ranger_ros2` 0.2.0 / `ugv_sdk` 0.3.0 머지 완료.
두 저장소를 함께 보는 것이 맞아 한 문서로 적는다 — 수정 하나가 양쪽에 걸쳐 있는 경우가 많고,
**`ugv_sdk`는 정적 라이브러리라 SDK만 갱신하면 동작이 바뀌지 않는다.**

| | |
|---|---|
| PR | `ugv_sdk#12`(4커밋) → `ranger_ros2#7`(9커밋) |
| 검증 | 시뮬레이터(`ranger_can_sim`) + **실섀시 Ranger Mini 3.0에서 8개 항목 전부 통과** |
| 계기 | `cona_comm` 상태 허브를 이 드라이버 위에 올리면서, 필요한 값이 없거나 틀리게 나오는 것이 드러남 |

---

## 1. 왜 시작했나

`cona_comm`이 `/cona_comm/state`로 로봇 상태를 취합하려는데 두 가지가 막혔다.

- **배터리 `soh`가 ROS에 없다.** 섀시는 보내고 SDK도 파싱하는데 `sensor_msgs/BatteryState`에 담을 필드가 없어 버려지고 있었다. 사내 규정은 1일 1회 기록을 요구한다.
- **버스가 죽었는지 알 방법이 없다.** 이 노드는 마지막 상태를 50 Hz로 계속 재발행하므로 "메시지가 온다"가 살아있다는 근거가 못 된다.

파고들다 보니 **값이 틀린 것, 값이 아예 안 보이는 것, 값이 없는데 있는 척하는 것**이 함께 나왔다.

---

## 2. 고친 것

### 2.1 상수 두 개가 다른 기종 것이었다 — `ranger_ros2`

```
CONTROL_MODE_RC = 0     → 0은 standby, RC는 3
VEHICLE_STATE_ESTOP = 1 → 이 기종에 1은 존재하지 않음 (0 정상 / 2 이상)
```

**실로봇 16.3분 주행 기록 47,749 샘플**에서:

| control_mode | 샘플 | |
|---|---|---|
| 1 (CAN) | 38,013 | 79.6 % |
| **3 (RC)** | 9,731 | **20.4 %** |
| 0 (STANDBY) | 5 | 0.01 %, 전부 0.000초짜리 전이값 |

즉 상수를 믿고 `control_mode == CONTROL_MODE_RC`로 비교하면 **RC 조종 20.4 %를 전부 놓치고, 전이 중 스치는 5점을 RC로 오인**한다. `cona_comm` 쪽에서 실제로 이 비교를 쓰려던 참이었고, "명령은 있는데 실측이 0"인 29건 중 26건이 RC 구간이라 그대로 갔으면 오경보가 될 자리였다.

원인은 AgileX **계열 공용 enum을 기종 확인 없이 복사**한 것. Scout 매뉴얼이 정확히 `vehicle_state 0x01 = Emergency stop`, `control_mode 0x00 = Remote control`이다.

### 2.2 고장 코드가 실제 고장을 담지 못했다 — `ugv_sdk` + `ranger_ros2`

매뉴얼상 0x211의 고장 필드는 **byte[4..7] uint32 하나**인데, SDK 구조체가 이를 `error_code(2) + reserved + count`로 쪼개 **앞 2바이트만** 읽고 있었다. 그 2바이트에는 조향 영점 캘리브레이션 플래그뿐이고, 실제 고장은 전부 뒤 2바이트에 있다.

| 위치 | 내용 |
|---|---|
| byte[6] | 드라이버 상태, 5~8번 모터 통신, 과열, 과전류 |
| byte[7] | 배터리 저전압, 과전압, **RC 연결 상실**, 1~4번 모터 통신, **비상정지** |

실캡처에서 이 로봇이 실제로 보고하던 값이 그 영역이었다 — `0x100`(우전륜 드라이버 이상, 한 파일의 대부분인 53,801프레임), `0x4`(RC 상실), `0x180`(드라이버 이상 + 비상정지). **전부 ROS에서 `error_code = 0`으로 보였다.**

`error_code`는 그대로 두고 `error_code_full`(4바이트 전체)을 추가했다. 기존 필드는 Scout 계열에서는 올바른 정의이므로 넓히지 않았다.

실섀시에서 비상정지를 눌러 확인:
```
평상시 : error_code=0  error_code_full=0x00000000  vehicle_state=0
누른 뒤 : error_code_full=0x00000080  vehicle_state=2
```

> 비상정지를 **관측**할 수 있게 됐지만 **해제**는 여전히 불가하다. 매뉴얼상 해제는 0x441 프레임인데 SDK에 송신 API가 없다. 리모컨 KEY1로만 지울 수 있다.

### 2.3 값이 없을 때 0을 정상값으로 내보냈다 — `ranger_ros2`

SDK는 피드백 구조체를 프레임이 올 때까지 초기화하지 않고, `sensor_msgs/BatteryState`의 float 기본값은 `NaN`이 아니라 `0.0f`다. 그래서 노드가 뜨자마자 **0으로 채워진 메시지 한 세트**를 발행했다.

문제는 그 출력이 "데이터 없음"으로 읽히지 않는다는 것이다:

```
vehicle_state 0  = "시스템 정상"
motion_mode   0  = 유효한 모드(DUAL_ACKERMAN)
battery       0 V
```

**전원이 꺼진 섀시가 건강하게 정지해 있는 로봇과 구분되지 않는다.** 실제로 하류 소비자가 0 V를 현재 배터리 값으로 표시하고 있었다.

이제 피드백 그룹별로 스탬프가 찍혔는지 보고 발행을 게이트한다. 그룹이 독립이라 **BMS만 죽으면 나머지는 계속 발행**된다.

### 2.4 버스 생존을 판별할 수단이 없었다 — `ranger_ros2` + `ugv_sdk`

이 노드는 마지막 값을 고정 주기로 재발행하므로 메시지 도착은 생존의 근거가 못 된다. 그렇다고 값 변화를 보기도 어렵다 — 실캡처에서 **BMS 4필드가 481.6초, 0x211 필드가 91.7초** 동안 한 조합으로 머문 구간이 있다(만충 정차). 값만 보면 그만큼 기다려야 "죽었다"고 말할 수 있다.

그래서 그룹별 수신 카운터를 추가했다:

| 필드 | 그룹 |
|---|---|
| `SystemState.feedback_count` | 코어 (0x211/0x221/0x291/0x311/0x312) |
| `ActuatorStateArray.feedback_count` | 액추에이터 (0x251~8, 0x261~8, 0x271, 0x281) |
| `BmsState.feedback_count` | BMS (0x361) |

**발행되는 값은 항상 1 이상**이다(첫 프레임 전에는 발행 자체를 안 하고, 카운터는 발행 전에 증가). 따라서 `0`은 "버스 죽음"이 아니라 **"구버전 발행자"** 를 뜻한다 — 소비자가 두 상태를 섞지 않도록 계약으로 못박았다.

여기서 SDK 쪽 결함이 하나 드러났다. `ParseCANFrame`이 모든 프레임을 세 updater에 넘기는데 `UpdateActuatorState`만 **그룹 판별 switch 이전에** 타임스탬프를 찍고 있었다. 0x211 하나만 와도 액추에이터 그룹이 "갱신됨"으로 표시됐다는 뜻이다.

```
수정 전  0x211 만 주입 → /system_state +209, /actuator_state +208   ← 같이 증가, 정지가 안 보임
수정 후  0x211 만 주입 → /system_state +208, /actuator_state    0   ← 동결
```

### 2.5 명령 속도에 상한이 없었다 — `ranger_ros2`

`ranger_base`도 `ugv_sdk`도 선속도를 제한하지 않았고, SDK는 `(int16_t)(값 × 1000)`으로 캐스팅만 한다. 범위를 넘으면 **포화가 아니라 wrap**이다.

```
40 m/s 명령 → 40000 mm/s → int16 wrap → -25536 mm/s = 전속 후진
```

상류의 단위 착오 한 번이 최고속 후진이 되는 구조였다. `max_linear_speed`가 있긴 했으나 V1 전용 경로에만 걸려 있었다.

이제 속도를 담는 두 모드 모두에서 클램프하고, 매뉴얼의 두 번째 제한(조향 20° 초과 시 ±1000 mm/s)도 적용한다. 실섀시 CAN 프레임 실측:

```
vx=1.0        → 1000              vx=3.0                → 2000
vx=40.0       → 2000              vx=2.0 wz=3.0         → 1000 (조향 354)
vx=0.8 wz=2.0 →  800 (조향 553)   parallel x=3.0 y=1.0  → 1000 (조향 1570)
```

> **주의: 클램프는 전 기종에 걸린다.** V3만 매뉴얼 사양(7.2 km/h = 2.0 m/s)으로 올렸고 나머지는 기존 상수를 쓴다. 지금까지 제한이 없었으므로 **V1/V2 장비는 이전보다 느려질 수 있다.** 현장에 해당 기종이 있으면 사양 확인이 필요하다.

### 2.6 `soh`를 실을 곳을 만들었다 — `ranger_ros2`

`ranger_msgs/BmsState`를 `/bms_state`로 신설했다. 0x361을 그대로 옮긴다 — `battery_soc`, `battery_soh`, `voltage`, `current`, `temperature`, `feedback_count`. `/battery_state`는 그대로 두었다.

`capacity`(Ah 필드)에 %를 넣는 것은 단위 오용이고, `SystemState`는 섀시 상태 성격이라 배터리 값이 섞이면 의미가 흐려진다고 판단했다.

**값에 대한 단서**: 0x361 byte[1]을 BLF 캡처 7개에서 직접 디코드하니 **74,301 프레임 전부 100**이었고 실로봇도 100이다. 같은 프레임의 SOC는 63~100으로 정상 변동한다. 즉 **값은 실재하고 채워지지만, 이 데이터로는 열화를 반영하는지 알 수 없다.** 기록 요건은 충족하되 "100이니 건강하다"로 읽으면 안 된다.

### 2.7 배터리 퍼센트 단위 — 파라미터로 열어두었다 — `ranger_ros2`

`sensor_msgs/BatteryState`는 `percentage`를 0~1로 규정하는데 이 노드는 섀시 원값 0~100을 내보낸다. 85 % 로봇이 `85.0`으로 나간다.

소비자들이 **현재 동작에 맞춰 만들어져 있어** 그냥 바꾸면 배포 순간 깨진다. `battery_soc_unit` 파라미터(`percent` 기본 / `ratio`)로 두어 배포 창을 맞춰 옮길 수 있게 했다. `/bms_state.battery_soc`는 어느 쪽이든 0~100이다.

영향 범위는 좁다 — `sensor_msgs/BatteryState`를 쓰는 곳은 이 노드(발행)와 `cona_comm`(구독) 둘뿐이고, ICN 계열은 이 메시지 타입을 아예 쓰지 않는다(`std_msgs/String` JSON).

### 2.8 CAN이 끊기면 노드가 죽었다 — `ugv_sdk`

실기 테스트 중 발견. 인터페이스를 내리면:

```
terminate called after throwing an instance of 'std::system_error'
  what():  Resource deadlock avoided
process has died [exit code -6]
```

읽기 완료 핸들러가 io 스레드에서 도는데, 에러 시 `Close()`를 부르고 그 `Close()`가 **자기 자신(io 스레드)을 join**한다. `EDEADLK` → `std::system_error` → 아무도 잡지 않아 `terminate()`.

**인터페이스가 준비되기 전에 노드가 뜨면 같은 경로로 즉시 죽는다.** 부팅 순서에 따라 로봇이 **드라이버 없이 부팅을 마칠 수 있다**는 뜻이다. 실기에서 두 번 재현됐다.

수정 후: 노드 생존, `CAN read failed on can0: Network is down` 로그, 마지막 값 계속 발행, 카운터 동결.

## 3. 실섀시 검증

`docs/ranger_beta_check.sh`로 8개 항목을 돌렸다. 전부 통과.

| # | 항목 | 결과 |
|---|---|---|
| 0 | 설치 버전 | 4/4 |
| 1 | PARALLEL 조향 + x 의존성 | 7/7 |
| 2 | 속도 클램프 | 3/3 |
| 3 | 발행 게이트 + 복구 | 6/6 |
| 4 | 카운터 동결 | 6/6 |
| 5 | 고장 필드 (비상정지) | 2/2 |
| 6 | BMS (`soh`) | 1/1 |
| 7 | 회귀 (ackerman/arc/spinning/파킹) | 3/3 |

**검증하지 못한 범위**: `ratio` 경로(실기 미실행), 그룹별 **독립** 동결(실섀시에서 그 조건을 만들 수 없음 — 시뮬레이터 + 수정 전 음성 대조로만 확인), 장시간·고속 주행, V3 외 기종.

### 3.1 실측값

주요 항목에서 실제로 나온 값. 숫자 없이 "통과"만 적으면 다음에 회귀가 나도 비교할 기준이 없다.

**PARALLEL 조향** — `linear.y`는 정규화 조향 명령이고 `linear.x`와 무관하다

| 명령 | 조향각 (기대) | 실측 |
|---|---|---|
| `x=0.2 y=+1.0` | +1.570 | +1.570 |
| `x=0.2 y=-0.5` | −0.785 | −0.785 |
| `x=0.0 y=+1.0` | +1.570 | +1.570 |
| `x=0.1 y=0.3` | +0.471 | +0.470 |
| `x=0.3 y=0.3` | +0.471 | +0.471 |
| `x=0.5 y=0.3` | +0.471 | +0.470 |

아래 세 줄이 **`x`를 바꿔도 조향각이 같다**는 직접 증거다. 실캡처 분석으로는 `x = −0.3` 구간 둘밖에 없어 크기 차이로만 갈랐던 부분이 여기서 닫혔다.

**속도 클램프** — CAN 프레임(0x111 linear, mm/s)에서 직접 확인

| 명령 | 결과 | 수정 전이라면 |
|---|---|---|
| `vx=1.0` | 1000 | 1000 |
| `vx=3.0` | 2000 | 3000 |
| `vx=40.0` | 2000 | **−25536** (int16 wrap = 전속 후진) |
| `vx=2.0 wz=3.0` (조향 354) | 1000 | 2000 |
| `vx=0.8 wz=2.0` (조향 553) | 800 | 800 |
| `parallel x=3.0 y=1.0` (조향 1570) | 1000 | 4243 |

**카운터 동결** — CAN 차단 시 메시지는 계속 발행되고 카운터만 멈춘다

```
차단 전 : system 287→720   actuator 363→799   bms 35→71
차단 후 : system 969 고정   actuator 969 고정   bms 77 고정
```

**고장 필드**

```
평상시   error_code=0  error_code_full=0x00000000  vehicle_state=0
비상정지  error_code_full=0x00000080              vehicle_state=2
```

**BMS**

```
battery_soc 84 · battery_soh 100 · voltage 49.7 V · current −1.8 A · temperature 36.7 ℃
```

**발행 게이트** — 프레임 없을 때 5개 토픽 전부 미발행, 복구 후 재개(`battery_voltage=50.1`)

> 이후 `27cb49f`에서 카운터가 wrap 시 0을 건너뛰도록 고쳤다. "발행 값은 1 이상"이 발행 게이트의
> 부수 효과가 아니라 카운터 자체의 성질이 되어, 소비자가 그 보장에 기대도 게이트 변경에 흔들리지
> 않는다. 소비자(`cona_comm`)는 `feedback_count == 0`을 구버전 발행자로 판정하는 데 쓴다.

### 3.2 조향 정착 시간 — 고정 기울기가 아니다

`ranger_can_sim`이 시뮬레이터 조향 모델을 실기에 맞추려면 **이동 시간이 목표각에 정비례하는지**를 알아야 해서 따로 측정했다(`1f` 항목). 목표마다 0으로 복귀시킨 뒤 `x=0`으로 조향만 움직였다.

| 목표(rad) | 명령→출발 | 이동시간 | 평균 기울기 | 정비례라면 예상 이동시간 |
|---|---|---|---|---|
| 0.2 | 1.27 s | 0.12 s | 1.60 rad/s | 0.07 s |
| 0.5 | 1.23 s | 0.22 s | 2.26 rad/s | 0.17 s |
| 1.0 | 1.26 s | 0.38 s | 2.67 rad/s | 0.35 s |
| 1.57 | 1.29 s | 0.54 s | 2.89 rad/s | 0.54 s (기준) |

**짧은 목표일수록 평균 기울기가 낮다** — 0.2 rad 이동이 정비례 예상의 1.7배 걸린다. 가속·감속 구간이 있어 짧은 이동은 정상 속도에 도달하지 못하는, 사다리꼴 속도 프로파일의 모습이다.

`ranger_can_sim` 쪽에서 이 4점에 최소제곱 피팅을 했고 잔차가 ±0.01초 이내로 들어왔다:

```
t(d) = d / 3.26 + 0.064
  정상 속도 vmax = 3.26 rad/s
  가감속 오버헤드 ta = 0.064 s  →  가속도 a = 50.7 rad/s²

  d=0.20  실측 0.12  예측 0.126     d=1.00  실측 0.38  예측 0.371
  d=0.50  실측 0.22  예측 0.218     d=1.57  실측 0.54  예측 0.546
```

사다리꼴이 성립하는 최소 거리는 `v²/a = 0.210 rad`이므로 **0.2 rad 측정점은 삼각 프로파일 경계에 걸쳐 있다**(정상 속도에 도달하기 전에 감속 시작). 그 점만 잔차가 양수로 나오는 이유이고, 0.21 rad 미만은 `t = 2√(d/a)`를 써야 한다.

**명령→출발 지연은 이동 거리와 무관하게 1.23~1.29초로 일정하다.** 기구 지연이 아니라 처리 경로의 고정 지연이다(명령 발행 → CAN 전송 → 섀시 수신·모드 확인 → 조향 개시). 계측 경로 지연도 일부 섞여 있으므로 절대값보다 **"거리 무관한 고정 지연이 존재한다"** 는 사실을 취하는 편이 안전하다.

이로써 **세 상수가 서로 다르다**는 것이 갈렸다:

| 상수 | 값 | 출처 |
|---|---|---|
| 모드 전환 게이팅 | 최대 0.57초 | 0x291 byte[1], BLF 332회 |
| 조향 정착 | 0.12~0.54초 (목표각에 따라) | 이번 실측 |
| 명령→출발 고정 지연 | 약 1.25초 | 이번 실측 |

시뮬레이터는 앞의 둘을 하나로 묶어 고정 기울기 1.6~2.0 rad/s로 모델링하고 있어, **1.57 rad 이동이 실기(0.54초)보다 1.8배 느리다**(0.97초). 안전 방향이긴 하나 타이밍에 의존하는 테스트는 시뮬레이터를 통과해도 실기 동작을 반영하지 못한다.

원인도 갈렸다. 시뮬레이터의 조향 속도 상수가 `SPIN_STEER_ANGLE / 0.6`으로, **모드 전환에 0.6초 걸린다는 관측에서 역산한 값**이었다. 실기 조향 속도가 3.26 rad/s면 같은 각도는 0.35초면 끝나므로, 0.6초는 조향 정착이 아니라 구동 게이팅 시간이었던 것이다. 두 상수를 하나로 뭉개면서 조향이 2배 느리게 모델링됐다.

### 3.3 측정하면서 틀린 것

검증 스크립트가 실기에서 세 번 연속 잘못된 결과를 냈다. 셋 다 **시뮬레이터에서는 통과**했고, 셋 다 **그럴듯한 숫자를 만들어냈다.**

| 무엇 | 증상 | 왜 시뮬레이터에서 안 드러났나 |
|---|---|---|
| `ros2 topic echo --field states[4]...` | 배열 인덱싱 미지원 → 빈 값 | 빈 값이 0으로 읽혀 "조향 0"으로 보임 |
| 명령이 끝난 뒤 측정 | 전부 0 | 시뮬레이터는 마지막 명령을 무기한 유지 |
| 고정 시점(2초) 샘플링 | 실행마다 다른 케이스가 실패 | 시뮬레이터는 램프가 빨라 항상 도달해 있음 |

추가로 `1f` 측정 자체에서 두 번 더 틀렸다 — 목표마다 0으로 복귀시키지 않아 **직전 각도에서 출발**한 것, `awk`의 `systime()`이 1초 단위라 **모든 간격이 0.00/1.00으로 반올림**된 것.

공통점은 **결과가 비어 보이지 않았다**는 것이다. 숫자가 나왔고 형식도 맞았다. 그래서 스크립트를 고쳐, 측정 실패·미출발·미도달·정착을 각각 다른 문구로 찍게 했다. 값 없음을 0으로 보고하지 않는다는 원칙은 드라이버 코드에만 해당하는 것이 아니었다.

## 4. 이 과정에서 드러난 다른 문제

드라이버 코드 밖이지만 같이 기록해 둔다.

**① 크로스 빌드된 파이썬 typesupport가 로봇에서 임포트되지 않는다**
arm64 deb인데 확장 모듈 이름이 `cpython-310-**x86_64**-linux-gnu.so`로 생성된다. 파이썬은 자기 ABI 태그와 맞는 것만 임포트하므로 파일이 있어도 없는 것으로 처리한다. C++ 노드는 영향 없지만 `ros2 topic echo`와 파이썬 노드가 전부 깨진다. 심볼릭 링크로 우회 가능하나 재설치하면 사라진다. **크로스 빌드된 모든 메시지 패키지에 해당할 수 있다.** apt 파이프라인 쪽에서 정식 수정 진행 중.

**② 정적 링크 의존자가 자동 재빌드되지 않는다**
`ugv_sdk`는 `libugv_sdk.a`로만 배포된다(`.so` 없음). SDK deb만 갱신하면 `ranger_base_node` 안의 옛 코드가 그대로 돈다. **버전 번호는 올라가는데 동작은 그대로**라 가장 알아채기 어려운 형태다. 이번에 크래시 수정을 반영할 때 실제로 이 함정에 빠졌다. 규칙: **`ugv_sdk`만 바뀌어도 `ranger_base`를 재빌드해야 한다.**

**③ `/cmd_vel`에 발행자가 둘이면 명령이 섞인다**
테스트 중 조향각이 실행마다 무작위로 달라졌는데, 다른 노드가 `/cmd_vel`을 같이 쏘고 있었다. 두 명령이 번갈아 들어가면 드라이버가 PARALLEL↔DUAL_ACKERMAN을 오가며 조향 목표가 0과 목표값 사이를 **물리적으로 왕복**한다(`0.001 → 0.025 → 0.000 → 0.024 …`). 관측되는 명령은 **어느 발행자의 의도도 아니다.** 운영 중에도 같은 일이 나므로, 명령과 실측을 비교하는 소비자는 발행자가 하나인지 먼저 확인해야 한다.

## 6. 배포 시 주의

1. **`ugv_sdk`를 먼저** 머지·빌드하고 **그다음 `ranger_ros2`**. 건너뛰면 `error_code_full`이 조용히 항상 0이 되고 액추에이터 카운터가 틀린다.
2. **`ranger_base`는 SDK만 바뀌어도 재빌드**해야 한다(정적 링크).
3. 설치는 **네 패키지를 한 번에**. 일부만 깔면 `ranger_msgs`만 새것이 되어 새 필드가 0으로 읽힌다.
4. 로봇에서 `ros2 topic echo`가 안 되면 파이썬 typesupport 심링크를 다시 걸어야 한다(위 ①).
