# ranger_ros2 → cona_comm 토픽 계약 (실측 기준)

작성 2026-09-10, 갱신 2026-09-14. 대상: `cona_comm` 상태 허브(`/cona_comm/state`) 파서.

> **2026-09-14 갱신 주의**: 최초 작성분은 `ranger_ros2` `d0ccbf6` / `ugv_sdk` `c897ba6` 기준이었는데,
> 그 시점에 원격이 이미 9커밋(ranger_ros2) / 2커밋(ugv_sdk) 앞서 있었고 이 문서는 그것을 모른 채
> 작성됐다. 아래 내용은 **현재 `origin/humble` + `origin/main` 기준으로 재확인·정정한 것**이다.
> 본문의 파일 줄번호는 갱신 시점 기준이며, 그 이후 이동했을 수 있다.

검증 대상: `ranger_ros2` `origin/humble` `57111f4` + 이 브랜치의 5커밋,
`ugv_sdk` `origin/main` `e9ee90a` + 2커밋.

## 검증 환경과 신뢰 등급

`ranger_can_sim` 시뮬레이터 ↔ vcan0 ↔ 실제 `ugv_sdk` + `ranger_base_node`(`ROS_DOMAIN_ID=42`).
값의 출처를 3등급으로 표기한다. **[M]** 매뉴얼(RANGER MINI 3.0 User Manual, 41p) 근거로 확정,
**[R]** 실섀시 BLF 캡처(8개·4.4시간) 근거로 확정,
**[S]** 시뮬레이터 관측값이며 실장비 근거 없음 → **하드코딩 금지**.

**[R]의 대부분은 같은 캡처 세트 하나에서 나온다** (`can_combined_20260902_*.blf` 8개, 차량 1대,
같은 날). 여러 세션이 같은 수치를 얻었다고 적힌 항목도 대개 **같은 데이터를 각자 계산한 검산**이지
다른 데이터에서의 재현이 아니다. 검산도 값어치는 있지만(실제로 이 대조로 `0x291` 바이트를 잘못
읽던 버그가 드러났다) **"다른 조건에서도 성립한다"는 근거는 되지 못한다.** 별도 근거를 가진 것은
실기 직접 측정(조향 램프 4점, `0x80` 비상정지, 리모컨 끔 → `0x4`)과 `cona_comm`의 `20260911`
ROS bag이며, 기종 일반화에는 **다른 개체**가 필요하다 — 위 전부가 같은 차량이다.

## 2026-09-14 변경 요약 — 이전 판을 읽었다면 여기부터

이 갱신으로 계약이 바뀐 항목:

- **`/cmd_vel`의 `linear.y` 의미가 바뀌었다** (원격 `31dd1c7`). PARALLEL 모드에서 `y`는 횡속도가
  아니라 **정규화된 조향 명령 `[-1, 1]`** 이고(최대 조향각의 비율, +1 = 좌 90도), `x`가 그 방향의
  속도(m/s)다. `x=0`이면 바퀴 각도만 유지하고 주행하지 않는다. **명령과 실측을 비교하는 소비자는
  PARALLEL 구간에서 `|cmd|`와 `|odom.twist|`를 직접 비교하면 안 된다** — 단위가 다르다.
- **`/system_state`에 필드 2개 추가**: `error_code_full`(0x211 byte[4..7] 전체), `feedback_count`.
- **`/actuator_state`에 `feedback_count` 추가**, **`/bms_state`(`ranger_msgs/BmsState`) 신설**.
- **첫 CAN 프레임 수신 전에는 아무 토픽도 발행하지 않는다**(그룹별).
- **`/cmd_vel_manager/control_mode`(`std_msgs/UInt8`) 구독 추가**. 노드가 제어모드를 주기적으로
  재전송하며(`control_mode_period`, 기본 1.0초), 이 토픽으로 외부 커맨더가 목표값을 바꾸면 그것을
  유지한다. 즉 standby에 머무는 구간은 사라지고, 외부 커맨더가 있으면 그쪽이 우선이다.
- 파라미터 추가: `battery_soc_unit`(`percent` 기본 / `ratio`), `control_mode`, `control_mode_period`,
  `cmd_deadzone`.

## 토픽 목록 (실측)

| 토픽 | 타입 | 주기 | QoS |
|---|---|---|---|
| `/system_state` | `ranger_msgs/msg/SystemState` | 50.0 Hz | RELIABLE |
| `/motion_state` | `ranger_msgs/msg/MotionState` | 50.0 Hz | RELIABLE |
| `/battery_state` | `sensor_msgs/msg/BatteryState` | 50.0 Hz | RELIABLE |
| `/actuator_state` | `ranger_msgs/msg/ActuatorStateArray` | 50.0 Hz | RELIABLE |
| `/odom` | `nav_msgs/msg/Odometry` | 50.0 Hz | RELIABLE |

주기는 CAN 프레임 주기가 아니라 노드의 `update_rate`(기본 50) 폴링 주기다. 즉 **같은 CAN 값이
여러 번 재발행된다.** BMS(0x361)는 매뉴얼 500 ms·실측 약 250 ms 주기이므로 `/battery_state`는
같은 값을 약 12회 반복 발행한다. 변화 감지는 값 비교로 하고, 수신 시각을 갱신 시각으로 쓰지 말 것.
자세한 고착 시간 분포는 "신선도(끊김) 판정" 절 참조.

`header.stamp`는 전 토픽이 노드의 발행 시점(`node->get_clock()->now()`)이다. CAN 수신 시각이
아니므로 **프레임 지연·유실을 stamp로 판정할 수 없다.**

## `/system_state`

```
uint8   vehicle_state    0x211 byte[0]
uint8   control_mode     0x211 byte[1]
uint16  error_code       0x211 byte[4..5]  ← 주의, 아래 참조
float64 battery_voltage  0x211 byte[2..3], 0.1 V 단위
uint8   motion_mode      0x291 byte[0]
```

### `ranger_msgs/SystemState.msg`의 상수 정의를 쓰지 말 것

메시지 파일에 선언된 상수 중 둘이 실제와 다르다. **[M]**

| 메시지 상수 | 실제 (매뉴얼 0x211 표) |
|---|---|
| `VEHICLE_STATE_NORMAL = 0` | 맞음 (0x00 system normal) |
| `VEHICLE_STATE_ESTOP = 1` | **1은 존재하지 않는 값.** 매뉴얼에 0x00/0x02 뿐 |
| `VEHICLE_STATE_EXCEPTION = 2` | 맞음 (0x02 system abnormal) |
| `CONTROL_MODE_RC = 0` | **0은 standby.** RC는 **3** |
| `CONTROL_MODE_CAN = 1` | 맞음 (0x01 command control mode) |
| (없음) | **standby = 0** 상수가 없음 |

권고 매핑: `vehicle_state` → `0 normal / 2 abnormal` (그 외 값은 unknown으로 통과),
`control_mode` → `0 standby / 1 can / 3 rc` (그 외 unknown).

`ugv_sdk`의 enum은 올바르다 — `agilex_types.h:36-41`이
`CONTROL_MODE_STANDBY=0x00 / CAN=0x01 / UART=0x02 / RC=0x03`이다. 즉 **틀린 것은
`ranger_msgs/SystemState.msg`의 상수 선언뿐**이다. SDK의 `UART=0x02`는 계열 공용 enum이고
이 기종 매뉴얼에는 없으며 관측된 적도 없으므로 `unknown`으로 처리하면 된다.
(SDK의 `AgxVehicleState`도 `VEHICLE_STATE_ESTOP=0x01`을 갖고 있는데 이 역시 이 기종 매뉴얼에
없는 값이다.)

실로봇 ROS bag 실측 **[R]** (`20260911_132337_full_CC0Enu`, 16.3분 주행, `/system_state`
47,749 샘플):

| control_mode | 샘플 | 비율 |
|---|---|---|
| `1` (CAN) | 38,013 | 79.6 % |
| **`3` (RC)** | 9,731 | **20.4 %** |
| `0` (STANDBY) | 5 | 0.01 % |

`1` ↔ `3` 전환 경계에서 `0`이 한 틱 스친다. 따라서 메시지 상수를 그대로 믿고
`control_mode == CONTROL_MODE_RC`로 비교하면 **RC 조종 구간 20.4 %를 전부 놓치고, 모드 전환
순간 5건을 RC로 오인한다.** `vehicle_state`는 같은 세션 47,749 샘플 전부 `0`이었다.

이 필드는 대체 수단이 없다: "명령은 0인데 로봇이 움직인다"가 RC 조종(정상)인지 폭주(이상)인지
가르는 것이 `control_mode`뿐이다. 실제로 같은 세션에서 "명령 있는데 실측 0" 29건 중 26건이
RC 구간이었다 — 상수를 그대로 썼다면 26건이 전부 오경보가 된다.

정상 시퀀스 실측: 노드 시작 전 `control_mode = 0`(standby) → 노드가 시작 시 0x421을 **1회** 전송
→ `control_mode = 1`. 노드는 이후 0x421을 재전송하지 않는다.

### `error_code`는 조향 캘리브레이션 정보만 담는다 — 고장 판정에 쓸 수 없다

근본 원인은 "상위 2바이트를 안 싣는다"가 아니라 **SDK가 필드 경계를 잘못 잡았다**는 것이다.
매뉴얼 0x211의 error message는 **byte[4..7] uint32 하나**인데(`unsigned int32`, byte[4]가 최상위),
`ugv_sdk`의 `SystemStateFrame`(`src/protocol_v2/agilex_protocol_v2.h:188`)은 같은 4바이트를
`struct16_t error_code` + `uint8_t reserved0` + `uint8_t count`로 쪼갰다. 그래서 파서
(`agilex_msg_parser_v2.c:73-75`)는 byte[4..5]만 uint16으로 읽고, byte[6..7]은 "예약 + 카운터"로
간주해 버린다. `ranger_messenger.cpp:247`이 이 잘린 값을 그대로 발행한다.
실캡처에서 byte[6..7]의 프레임 간 증분은 **171,460회 전부 0**이며 취한 값도 `0x01`(byte[6],
드라이버 상태)·`0x04`·`0x80`(byte[7], RC 연결 상실·비상정지)뿐이다 **[R]** — 카운터가 아니라
고장 비트임이 실측으로 확인된다.

0x211을 직접 주입해 측정한 결과 **[M]** + 실측:

| 주입 프레임 | `/system_state` |
|---|---|
| `00 01 01 E0 00 00 00 00` | vehicle_state 0, error_code 0 |
| `02 01 01 E0 01 00 00 00` (byte4=0x01) | vehicle_state 2, error_code **256** |
| `02 01 01 E0 00 0F 00 00` (byte5=0x0F) | vehicle_state 2, error_code **15** |
| `02 01 01 E0 00 00 01 00` (byte6=0x01) | vehicle_state 2, error_code **0** |
| `02 01 01 E0 00 00 00 80` (byte7 bit7 = E-STOP) | vehicle_state 2, error_code **0** |

즉 `error_code == (byte[4] << 8) | byte[5]` 이고, 매뉴얼 Table 1 기준 그 두 바이트의 내용은:

- byte[4] bit0~7: **전부 reserved (기본 0)**
- byte[5] bit0~3: 우전륜/우후륜/좌후륜/좌전륜 **조향 영점 캘리브레이션 이상**
- byte[5] bit4: 조향 캘리브레이션 타임아웃
- byte[5] bit5~7: reserved

**`/system_state.error_code`로 관측 불가능한 고장** (byte[6..7]에 있으나 SDK가 읽지 않음):

- byte[6]: 드라이버 상태, 5~8번 모터 드라이버 통신 이상, 과열 보호, 과전류 보호
- byte[7]: **배터리 저전압**, 과전압, **RC 연결 상실**, 1~4번 모터 드라이버 통신 이상, **비상정지**

실캡처에서 실제로 나타나는 error 값이 바로 이 영역에 있다 **[R]**: uint32(byte4..7) 기준
`0x100`(byte6 bit0 = 드라이버 이상, 172338 파일의 대부분인 53,801프레임), `0x4`(byte7 bit2 = RC 연결
상실, 11,509프레임), `0x180`(드라이버 이상 + 비상정지, 1,124프레임). **이 값들은 모두
`/system_state.error_code`에서 0으로 보인다.**

→ 파서 권고: **`error_code == 0`을 "정상"으로 해석하지 말 것.** 이상 여부는 `vehicle_state == 2`로
판정하고, `error_code`는 0이 아닐 때만 조향 캘리브레이션 계열로 해석한다. `ugv_sdk`의
`SYSTEM_ERROR_*_MASK`(`agilex_message.h:64-73`)는 Scout 계열 정의이고 Ranger Mini 3.0의
바이트 배치와 맞지 않으므로 쓰지 말 것.

### 비상정지는 관측도 해제도 불가 — `ems` 를 채울 수 없다

- **관측 불가**: 비상정지 비트는 0x211 byte[7] bit7이고, 위에서 본 대로 SDK가 byte[4..5]만 읽는다.
  `vehicle_state == 2`(abnormal)까지만 알 수 있고 원인이 비상정지인지는 알 수 없다.
- **해제 불가**: 매뉴얼은 비상정지 버튼을 풀고 나서 *"In command mode, you need to clear the emergency
  stop error through the clear error command"* 라고 명시한다 **[M]**. 그 명령은 0x441이고
  `ugv_sdk`에 프레임 정의(`agilex_protocol_v2.h:117` `CAN_MSG_STATE_RESET_CONFIG_ID`,
  `StateResetConfigFrame`)와 디코드 경로는 있으나 **송신 API가 없다** — `RangerInterface`에
  clear-error 메서드가 없고(`ranger_interface.hpp:65-75`), `AgxMsgStateResetConfig`는 메시지 union과
  파서에만 등장한다. `ranger_base`가 노출하는 서비스도 `/set_parking_mode` 하나뿐
  (`ranger_messenger.cpp:185`가 유일한 `create_service`).

→ Ranger Mini 3.0에서는 상류가 비상정지를 **관측할 수도 해제할 수도 없다.** 규정상 `ems`가
트리거 소스 배열을 요구한다면 이 플랫폼은 값을 실을 수 없으므로 빈 배열로 두고,
이상 여부만 `vehicle_state`로 표현하는 것이 맞다.

## `/motion_state`

`motion_mode`: `0 DUAL_ACKERMAN / 1 PARALLEL / 2 SPINNING / 3 PARKING / 4 SIDE_SLIP`.
`MotionState.msg`의 상수는 **정확하다** — 그대로 사용 가능 **[M]**.

- 파킹 진입/해제 실측: 서비스 `/set_parking_mode`(`std_srvs/srv/SetBool`) → true 시 `motion_mode 3`,
  false 시 `0`. 파킹 중에는 노드가 0x111을 한 프레임도 보내지 않는다(3초간 20 Hz cmd_vel → 0프레임).
- 모드 전환 중 섀시는 속도 명령에 무응답이며 **[M]**, 실측 전환 소요는 최대 0.57초·평균 0.13~0.18초
  **[R]**. 노드에 min-dwell 0.6s + 히스테리시스가 있어(커밋 `7a0b51b`) 20 Hz로 경계를 왕복시켜도
  0x141이 5초에 1~2회만 나간다. 상류에서 `motion_mode`가 튀는 것은 관측되지 않았으므로
  허브 쪽 디바운스는 불필요.
- **min-dwell 0.6s의 근거는 처음 생각보다 약하다** (2026-09-14). 이 값은 매뉴얼 문구("모드 전환
  중에는 속도 명령에 응답하지 않는다")와 실캡처의 0x291 byte[1] 전환 플래그 **최대 0.57초**에
  기대고 있었는데, 그 플래그를 전환 종류별로 나눠 보니 **지속시간이 0.08~0.36초(중위)로 이동
  거리와 무관**하고, 무엇보다 **모드 변경 941회 중 플래그가 선 것은 439회(47%)뿐**이다 **[R]**.
  플래그가 절반 이상의 전환에서 아예 서지 않으므로, "플래그 최대 0.57초"를 "전환에 최대 0.57초가
  걸린다"로 읽을 수 없다. 현재 값은 관측된 플래그 최대치보다 크고 실기 회귀에서도 문제가 없었으나,
  근거는 **매뉴얼 문구 + 상한 추정**으로 봐야 한다. 확정하려면 `0x141` 송신 시각 → `0x281` 휠속도가
  0이 아니게 되는 시각을 같은 버스에서 재면 된다(ROS를 거치지 않으므로 계측 경로 지연이 섞이지 않는다).
- `SIDE_SLIP(4)`는 Ranger Mini **V1** 전용 경로다(`ranger_messenger.cpp:472`). V3에서는 나오지 않는다.

## `/battery_state` (`sensor_msgs/BatteryState`)

출처는 0x361(BMS 기본). 주기는 매뉴얼 500 ms **[M]**, 실측 약 4 Hz(≈250 ms) **[R]**.

| 필드 | 값 | 비고 |
|---|---|---|
| `voltage` | 48.0 실측 | 0x361 byte[2..3], **0.01 V 단위** **[M]**. 0x211의 전압은 0.1V 단위로 다름 |
| `percentage` | **0~100** (실측 85.0) | 0x361 byte[0] SOC `uint8 Range 0~100` **[M]**. `ranger_messenger.cpp:340`이 무변환 대입 → `sensor_msgs` 0~1 규약 위반. 파서 기본값 `percent`가 맞음 |

## CAN 무수신 상태가 "정상 유휴 로봇"으로 보인다 (Critical)

`ugv_sdk`의 `AgilexBase`는 피드백 상태 구조체(`common_sensor_state_msgs_`,
`core_state_msgs_` 등)를 **생성자에서 초기화하지 않는다**(`agilex_base.hpp:196-213` 선언만).
`ranger_messenger`는 데이터 유무 가드 없이 매 tick 그 값을 발행한다(`:331-352` 등).
`sensor_msgs/BatteryState`의 float 기본값은 `NaN`이 아니라 **0.0f**다.

vcan0에 **아무 프레임도 오지 않는 상태**로 노드만 띄워 실측한 결과 (0x361·0x211 모두 미수신):

```
/battery_state : voltage 0.0  current 0.0  percentage 0.0  temperature 0.0   ← 50 Hz로 정상 발행
/system_state  : vehicle_state 0  control_mode 0  error_code 0  battery_voltage 0.0
/motion_state  : motion_mode 0
/odom          : twist 전부 0
```

문제는 배터리에 그치지 않는다. **`vehicle_state == 0`은 "시스템 정상"이고 `motion_mode == 0`은
유효한 모드(DUAL_ACKERMAN)이므로, CAN이 완전히 죽은 상태가 "정상적으로 정지해 있는 건강한 로봇"과
구분되지 않는다.** 발생 조건: 노드 시작 직후 첫 프레임 도착 전, 섀시 전원 off, CAN 케이블·트랜시버
단선, BMS 퓨즈 단선.

소비자 쪽 판정 근거로 쓸 수 있는 것:

- **전 필드가 정확히 0인 페이로드는 거부**한다(`bios_board`가 all-zero CAN 프레임을 버리는 규칙과 동일).
- 가장 신뢰할 만한 단일 지표는 **`battery_voltage == 0`**이다. 실섀시 정상 전압 범위는 45~54 V이고
  **[M]**, SOC 10 % 미만에서는 섀시가 외부 전원과 드라이버를 차단하므로 0 V가 정상값으로 나올 수 없다.
  `/system_state.battery_voltage`(0x211, 20 ms 주기)와 `/battery_state.voltage`(0x361) 두 경로가 모두
  0이면 무수신으로 판정해도 안전하다.
- `error_code == 0`·`vehicle_state == 0`을 건강 신호로 쓰면 안 되는 이유가 하나 더 늘어난 셈이다.

근본 수정은 상류에서 첫 프레임 수신 전 발행을 막는 것이다(`ranger_base`에 수신 플래그 가드 추가).
**미조치 상태이며 사용자 승인 대기.** `cona_comm` v1은 소비자 쪽 all-zero 거부로 닫혔다.

## 신선도(끊김) 판정 — 메시지 수신만으로는 불가

`ranger_base`는 CAN 프레임을 폴링해 저장값을 50 Hz로 재발행한다. **CAN이 끊겨도 노드는 마지막
값을 계속 발행하므로, "메시지가 왔다"는 신선도 근거가 되지 않는다.** `header.stamp`도 노드 발행
시점이라 도움이 되지 않는다.

- BMS(0x361)는 매뉴얼상 500 ms 주기 **[M]** 이나, 실캡처 실측은 **약 4 Hz(≈250 ms)** 다 **[R]**
  (87,555 프레임 / 약 21.7 ks). 즉 `/battery_state`는 같은 값을 **약 12회** 반복 발행한다.
  반복 자체는 이상 신호가 아니다.
- 0x211(vehicle_state·control_mode·error_code·battery_voltage)과 0x291(motion_mode)은 **20 ms 주기**이고
  0x211의 수신 타임아웃은 None이다 **[M]**. 배터리 도메인과 시스템 도메인에 같은 임계를 쓰면
  끊김을 20배 이상 늦게 잡는다. 수신 타임아웃 500 ms가 명시된 프레임은 0x111(호스트→섀시 명령)뿐이다.
- 따라서 값 변화 기반 판정이 필요하다. 도메인 페이로드가 직전과 같으면 수신 시각을 갱신하지 않고,
  변화가 있을 때만 갱신하는 방식(`bios_board`가 0x611 원시 페이로드 비교로 BMS freeze를 잡는 것과 동일).
- 임계는 CAN 주기가 아니라 **"값이 바뀔 것으로 기대되는 최대 간격"** 으로 잡아야 한다.

### 실캡처 재생 종단 검증: 정상 고착과 죽은 버스는 배터리 도메인에서 구분 불가 **[R]**

실섀시 캡처 재생 프레임(만충 대기 구간)이 vcan0에 흐르는 동안 실제 `ranger_base_node`를
통과시켜 관측한 결과 (계측기 t=0 = 2026-09-10 21:53:25):

```
[  115.6s / 21:55:21] BMS 4필드 조합 마지막 변화 → v=53.0 i=0.0 soc=100 temp=29.2
[  510.5s / 22:01:56] 재생 프레임 중단, 버스 완전 무음 (candump 0 프레임)
[  590.0s / 22:03:15] 같은 조합 계속 유지 중 — 474.4초 경과, 이후로도 무한
```

> **재생 출처**(2026-09-14 확정): 사용자가 직접 실행한 재생이었다. 처음에는 출처를 확정하지
> 못한 채 기록했고, 이후 실행 주체가 확인됐다. **다만 435초에서 끊긴 이유는 여전히 미확정**이다.
> 0x361 원시 페이로드
> `64 64 14 B4 00 00 01 24`(voltage 53.0 V / current 0.0 A / soc 100 % / temp 29.2 ℃)가
> `can_combined_20260902_102045.blf` 만충 대기 구간의 독립 BLF 분석 예측값과 정확히 일치하므로
> 입력이 그 실캡처 구간이라는 점은 확인되지만, **아래 시각 경계와 구간 길이는 재생이 중간에
> 끊긴 값이다**(캡처상 고착 481.6초 중 약 395초만 관측). 그 수치를 캡처 통계로 인용하지 말 것.
> 결론 자체(정상 고착과 죽은 버스가 `/battery_state`에서 동일하다, 0x211 디더링으로 버스 생존을
> 판정할 수 있다)는 재생 출처·길이와 무관하게 성립한다.

- **115.6 s ~ 510.5 s (약 395초)** 는 실섀시의 **정상 고착**이다(만충 대기, 0x361 원시 페이로드
  `64 64 14 B4 00 00 01 24` 79프레임 전부 동일, `/battery_state` 601 메시지의 float 비트까지
  유니크 조합 1개).
- **510.5 s 이후**는 **버스가 죽은 상태**다.
- `/battery_state`만 보면 이 둘이 **완전히 동일하다.** 죽은 버스에서 지금도
  `voltage 53.0 / percentage 100 / temperature 29.2 / current 0.0`, `vehicle_state 0`이 흐른다 —
  값이 그럴듯해서 정적 검사로 걸리지 않는다.
- 즉 **배터리 도메인의 고착 시간 임계로는 죽은 버스를 잡을 수 없다.** 481.6초 이상으로 잡으면
  단선을 최소 8분간 못 잡고, 그보다 낮게 잡으면 정상 만충 대기를 오탐한다. 분리 가능한 임계가 없다.

**시스템 도메인은 구분한다.** 같은 구간에서 `/system_state.battery_voltage`는 0x211(20 ms 주기,
0.1 V 양자화)의 디더링으로 55.2 ↔ 55.3 V를 계속 오갔다(고착 구간 동안 유니크 조합 1,417개).
그리고 **510.5 s에 정확히 멈췄다.**

→ 권고: **버스 생존(liveness)은 `/system_state`로 판정하고, 배터리 도메인에서 유도하지 말 것.**
0x211이 20 ms 주기이고 전압 하위 자리가 상시 흔들리므로 1~2초 안에 단선을 잡을 수 있다.
그러면 배터리 도메인 임계는 "BMS 계통만 죽은 경우"(0x361은 멈췄는데 0x211은 계속)만 담당하면 되고,
이 조합은 실제로 분리 가능하다.

| | 정지 | 91.7 s | 3.82 s | 0.084 s |

임계 권고:

- 0x211 값 변화로 생존을 판정하려면 **91.7초 + 마진 → 120초 이상**. 3.0초로 두면 p99(3.42초)보다
  낮아 정상 동작 중 고착의 1 % 이상에서 오탐하고, 정지 상태에서는 최악 92초간 오탐이 지속된다.

- 배터리 도메인(481.6초)보다 5배 이상 낫지만, **값 변화 방식으로 단선을 92초 안에 잡는 것은
  불가능하다.** 근본 해결은 `ranger_ros2`가 CAN 프레임 수신 시각 또는 수신 카운트를 토픽으로
  노출하는 것이다(미조치, 사용자 승인 대기). 그 경우 게이트는 1~2 프레임(약 40 ms) 만에 단선을

  배터리 값은 실제로 거의 정확하다(만충 대기 중 전압이 변할 이유가 없다). 정지 중 단선을
  아예 못 잡는 선택지 2는 기각 — 로봇이 정지해 있을 때가 사람이 접근하는 시점이다.

산출 조건은 아래 0x361 표와 동일(클램프 누적 시계, 4체인 절단으로 **max는 하한**, 차량 1대
4.4시간 세션).

  (8,129.7 / 555.7 / 88.5초)에서 체인을 끊었다. **끊는 시점에 진행 중이던 고착 구간은 버렸으므로
  위 max는 하한이다** — 실제 상한은 더 길 수 있다. 6,626.5초 soc 구간은 체인 1(3.72시간) 안의 값.
- 긴 구간(수백 초 이상)의 주행/정지 라벨은 신뢰하지 말 것. 분류가 "고착 구간이 끝난 시점"의 |v|
  기준이라, 대부분 정지였던 구간이 마지막에 움직였다고 주행으로 분류된다(soc의 주행측 6,626.5초가 그 예).
- 차량 1대·1회 세션 기준이므로 다른 팩·온도 조건에서는 달라질 수 있다. `soh`는 전 구간 100 고정이라 제외.

## `/actuator_state` (`ranger_msgs/ActuatorStateArray`)

`states[]`는 **항상 8개**(`ranger_messenger.cpp:302` 무조건 8회 push_back).

인덱스 매핑: id 0~3 = 구동 모터, id 4~7 = 조향 모터. 물리 위치는
**[전우 RF, 후우 RR, 후좌 LR, 전좌 LF]** 순 **[R]**.

구조적으로 0인 필드 (측정값 0과 구분해야 하므로 키 제거 권고). parallel 45° 주행 중 실측:

```
id 0~3 : rpm 132, motor_speeds 0.282, motor_angles 0.0     ← angles 구조적 0
id 4~7 : rpm 0,   motor_speeds 0.0,   motor_angles 0.785   ← speeds/rpm 구조적 0
```

- `motor_speeds[0..3]`, `motor_angles[4..7]`만 유효. `motor_angles[0..3]`는 코드가 0을 채우고
  (`ranger_messenger.cpp:296`), `motor_speeds[4..7]`도 0을 채운다(`:294`).
  `rpm[4..7]`은 0x251~8 HS 프레임 자체가 조향 모터에 대해 0이다.
- **(정정) `rpm`에도 부호는 있다 — 기준 좌표계가 다를 뿐이다** **[R]**. 앞서 "`rpm`에는 방향
  부호가 없다"고 적었던 근거는 제자리 회전 한 조건만 본 것이었다. 실캡처 8조각
  (`20260902`, 액추에이터 약 17만 샘플)을 `0x221` 피드백으로 조건별로 나누면:

  ```
  직진 전진 (steer≈0, lin>+0.15)   rpm + + - -    n=72,968   부호 일치 99.9%
  직진 후진 (steer≈0, lin<-0.15)   rpm - - + +    n= 5,167   100%
  제자리회전 좌 (ang>+0.3)          rpm + + + +    n= 5,250   99.98%
  제자리회전 우 (ang<-0.3)          rpm - - - -    n= 4,460   99.98%
  ```

  `rpm`은 **모터 로컬 좌표**, `motor_speeds`(0x281 유래)는 **차체 좌표**다. 좌우 모터가 거울상으로
  장착되어 있어 직진에서는 로컬 부호가 갈리고(`+ + - -`), 제자리 회전에서는 그 거울상이 차체
  기준 반대 회전을 상쇄해 넷이 같아진다(`+ + + +`). 두 관측은 **같은 규칙의 두 얼굴**이다.
  → **방향 판정에는 `motor_speeds` 또는 `/odom.twist`(0x221)를 쓸 것.** `rpm`은 원시값으로만
  다루고 부호로 진행 방향을 유도하지 말 것. `cona_comm`이 같은 결론을 9/11 캡처로 독립 도출했다.
- **`rpm[4..7]`(조향 모터)은 실값이다 — 다만 부호는 쓰지 말 것** **[R]**. 앞서 "전 구간 평균이 0
  근처라 잡음"이라고 적었는데, 전체 평균만 본 탓이고 틀렸다. 조향각 변화율(`0x221` byte[6..7]의
  미분)로 구간을 나누면 크기가 뚜렷하게 따라온다:

  ```
  |변화율| < 0.02 rad/s   비영 5~10%    |rpm| 중위    0   n=960,317
  0.02 ~ 0.3             비영 96%      |rpm| 중위   67   n= 37,634
  0.3  ~ 1.5             비영 99%      |rpm| 중위  380   n= 26,575
  > 1.5                  비영 98%      |rpm| 중위 1850   n= 12,743
  ```

  → **정지 중 0 근처인 것은 잡음이 아니라 실제로 조향 모터가 안 돌기 때문**이고, 조향이 움직이면
  그만큼 값이 커진다.

  **관계는 부호까지 결정적이다** **[R]**:

  ```
  rpm[i] = s × d(angle[i])/dt           angle[i] = 0x271의 코너별 조향각 (0.001 rad)
  s = -723  (CAN 경로 기준, 구간 -713 ~ -734)
  ```

  **하나의 값으로 적을 수 없다 — 추정 방향에 따라 갈리고 양쪽 다 편향이다.** CAN 경로,
  `|rate|>0.3` 필터, 모터 5~8 (n≈37,000씩):

  ```
  rpm ~ rate   -712.3 / -712.5 / -713.2 / -714.0    변화율의 잡음이 기울기를 0쪽으로 당김
  rate ~ rpm   -733.7 / -733.8 / -733.9 / -733.9    rpm의 잡음이 반대로 당김
  기하평균     -722.9 / -723.1 / -723.5 / -723.9    직교회귀 근사
  ```

  변화율에 잡음이 있는 이유는 `0x271`이 0.001 rad 양자이고 프레임 간격이 21 ms라
  **변화율의 양자가 0.048 rad/s**이기 때문이다. 참값은 두 방향 사이에 있고 `-723`이 최선
  추정이다. **`-713`을 참값으로 인용하지 말 것** — 이 문서도 한동안 그렇게 적고 있었다.

  **방향과 필터는 독립이 아니다.** `rate=0, rpm≠0` 쌍은 `rpm ~ rate`에서는 분자·분모 모두 0이라
  기여가 없지만, `rate ~ rpm`에서는 **분자에만** 들어가 반대로 민다. 임계를 훑으면:

  ```
  필터            n          rpm~rate   rate~rpm   기하평균
  rate==0 포함    4,149,080    -712.7     -776.8     -744.0
  |rate|>0 (엄격)   294,940    -712.7     -739.1     -725.8
  |rate|>0.05       237,960    -712.7     -737.6     -725.1
  |rate|>0.30       148,222    -713.0     -733.8     -723.3
  |rate|>1.00        70,014    -716.9     -730.0     -723.4
  ```

  **첫 줄과 둘째 줄의 차이가 전부다.** `rate==0` 표본이 3,854,140개인데 그중 292,779개는
  `rpm≠0`이다 — 두 프레임 사이에 각도가 양자 하나(0.001 rad)도 안 움직였는데 모터는 돌던
  구간, 즉 **`|rate| < 0.048 rad/s`가 전부 0으로 바닥친 것**이다. 값이 0인 게 아니라 측정이
  0으로 깔린 것이므로 빼는 게 맞다. 그 구간을 빼고 나면 기하평균이 임계에 거의 안 움직인다
  (-725.8 → -723.3 → -723.4). → **필터는 임의 선택이 아니라 양자화 바닥을 제거하는 것**이고,
  `-723~-725`가 임계 선택에 견디는 값이다. 다만 **"방향을 바꾸라"만 따르고 필터를 떼면
  -777이 나오므로** 방향·필터·경로 셋을 같이 적어야 한다.

  부호는 이 모든 것에 영향받지 않는다: **일치율 0.3~0.4%**
  — 즉 조향각이 커지면 rpm은 음수다. `ranger_can_sim`이 같은 캡처를 따로 계산해 -713.0을 얻었고
  (다른 데이터가 아니라 **검산**이다), 모드별로 나눠도 편차가 4% 이내다. `cona_comm`은 별도
  캡처(`20260911`, ROS bag)에서 같은 부호 규칙을 얻었다 — **부호는 두 데이터에서 확인됐다.**

  **경로가 다르면 다른 값이 나온다 — 개체·조건 차이가 아니다.** 위 값들은 `0x271` CAN 프레임
  간 차분이고, ROS 경로(bag)에서 미분하면 이 노드가 저장값을 50 Hz로 **재발행**한 것을 미분하게
  된다. 재발행 틱과 CAN 도착이 어긋나므로 어떤 틱은 변화율 0이 되고 어떤 틱은 두 프레임 분이
  한 번에 들어와, 변화율이 계통적으로 과대 추정되고 기울기는 과소 추정된다. 같은 캡처를 20 ms
  영차 유지로 재표본화해 확인했다:

  ```
  CAN 프레임 차분    -712.3 / -712.5 / -713.2 / -714.0
  50 Hz 재발행 모사  -669.6 / -669.1 / -669.8 / -667.8      (-6%)
  ```

  모사는 틱이 완벽히 주기적인 최선의 경우다. 틱에 지터를 넣으면 같은 방향으로 더 밀리고,
  **편향이 지터에 매우 민감하다**:

  ```
  지터 없음   -669      ±2 ms  -660      ±5 ms  -608      ±10 ms  -176
  ```

  `cona_comm` 실측이 수신시각 - `header.stamp` p95 4.5 ms이고 bag에서 얻은 값이 -626~-640이니
  위 곡선과 맞는다. **±10 ms에서 기울기가 4분의 1로 무너지는 것**에 주의할 것 — 발행 주기와
  같은 규모의 지터가 들어가면 미분값은 물리량과 무관해진다.

  재표본화 경로에서도 방향 차이가 같은 구조로 나타난다 — `rpm ~ rate` -671, `rate ~ rpm` -700.
  `cona_comm`이 bag에서 방향을 바꿔 -626~-640 → -681~-685를 얻어 CAN 경로와의 차가 12%에서
  4%로 줄었고, 남는 4%가 발행 지터다. → **ROS 토픽에서 잰 값과 CAN에서 잰 값을 같은
  물리량으로 비교하지 말 것.** 값을 옮길 때 추정 방법과 측정 경로를 같이 적을 것: 같은 데이터에
  비의 중위 / 필터 있는 비의 중위 / 최소제곱을 돌리면 525 ~ 748이 다 나온다.

  **위 비교에 `0x221` byte[6..7](섀시 대표 조향각)을 쓰면 안 된다.** 처음에 그렇게 해서 "부호가
  7~81%로 흩어진다"는 결론을 냈는데, DUAL_ACKERMAN에서는 앞축과 뒤축이 반대로 움직이므로
  **네 모터를 하나의 대표값과 비교하면 두 쌍이 갈려 나온다**(실제로 7/25 vs 62/81로 갈렸다).
  코너별 신호는 `0x271`이고, 대표 조향각은 `0x221` byte[6..7]이다. 크기는 둘이 같다 — 실캡처
  262,648 샘플에서 `|angle[i]| / |steer|` 중위가 정확히 1.000이라 **기어비 같은 환산은 없다.**

  다만 **소비자가 이 필드에 의존하는 것은 권하지 않는다**: 조향이 멈추면 0이고, 0에서는 아무
  정보가 없다.
- **`motor_angles[4..7]`의 정착 범위는 모드마다 다르고, DUAL_ACKERMAN은 내외륜이 차등이다** **[R]**.
  모드 레이블만으로 나누면 안 된다 — `0x291`은 명령 즉시 새 모드를 보고하지만 바퀴는 수백 ms 뒤에
  따라오므로 직전 자세가 꼬리로 섞인다(거르지 않으면 DUAL_ACKERMAN 범위에 PARALLEL의 1.569가
  들어온다). **모드 유지 1초 초과 + 조향 정지 0.5초 초과**로 거른 실측:

  ```
  DUAL_ACKERMAN  RF -0.698~+0.359  RR -0.359~+0.698  LR -0.698~+0.358  LF -0.359~+0.698
  PARALLEL       네 코너 전부 -1.569 ~ +1.571
  SPINNING       RF,LR -0.309~+0.936          RR,LF -0.936~-0.935
  PARKING        RF,LR -0.936~-0.935          RR,LF +0.935~+0.937
  ```

  같은 축의 두 바퀴가 **부호는 같고 크기가 다르다**(0.698 대 0.359, 1.94배). 교과서 Ackermann
  관계가 그대로 성립한다:

  ```
  cot(φ_바깥) - cot(φ_안쪽) = track / (wheelbase/2) = 0.364 / 0.247 = 1.474
  ```

  양축이 모두 조향하므로 유효 휠베이스가 절반이다. 앞축 안쪽각 대 바깥각 실측(중위, 정착 상태,
  28개 각도 구간·표본 3,479개, 같은 캡처의 필터 완화 재계산 — 모드 유지 0.5초 초과 + 조향 정지
  0.2초 초과(각도 변화 0.002 rad 미만)):

  ```
  안쪽    0.02   0.05   0.10   0.15   0.20   0.25   0.33   0.37   0.42   0.49   0.54   0.69   0.70
  바깥   0.022  0.045  0.086  0.124  0.154  0.183  0.223  0.242  0.263  0.290  0.307  0.356  0.358
  이론   0.019  0.047  0.087  0.123  0.155  0.183  0.224  0.242  0.263  0.290  0.308  0.356  0.359
  ```

  → **최대 오차 0.0034 rad로 전 구간에서 맞는다.** `0x271`의 양자가 0.001 rad이니 3양자 이내다.
  포화점 두 개의 우연이 아니라 관계식 자체가 성립한다. 이 대조는 `wheelbase`·`track`(0.494/0.364,
  지금까지 매뉴얼 근거뿐이던 값)에 실측 근거를 준다 — 다만 차량 1대다. **네 바퀴에 같은 |φ|를 가정하면
  안 된다.** (`0x221` byte[6..7]의 대표 조향각은 이 넷을 합친 값이므로, 코너별 값이 필요하면
  `motor_angles`를 봐야 한다.)
- `current`, `pulse_count`는 8개 모두 실값. `pulse_count`는 구동 모터(0~3)만 증가.
- `driver_state`(0x261~8 byte[5]): **실섀시는 완전 정상 상태에서 `0x40`(bit6)을 보고한다** **[R]**
  (error_code 0인 정상 캡처 4개에서 8모터 전부 예외 없이 0x40). 매뉴얼 Table 2는 bit6을
  "0: enable / 1: disable"로 적었으나 **실장비와 어긋난다**(매뉴얼 표기 오류 또는 펌웨어
  S-V6.0-8250218 극성 반대). → **`0x40` = 정상**으로 잡을 것. `0x00`도 구동 모터에서 간헐 관측된다.
  `0x20`(bit5 driver abnormal)은 이상이며, 실캡처에서 모터 0에 한해 0x211 error_code 0x100과
  동반해 나타난다. **이 `0x20`이 드라이버 고장을 잡는 유일한 상류 경로다** — 같은 고장이 0x211
  error_code에도 `0x100`으로 뜨지만 그 바이트는 SDK가 읽지 않아 `/system_state.error_code`에서
  사라진다(위 `error_code` 절). 실캡처에서 이 차량의 우전륜(모터 0) 드라이버 이상은
  `driver_state 0x20` 10,761프레임 + `error_code 0x100` 53,801프레임으로 존재했고, ROS 상류에서는
  전자만 관측 가능했다 **[R]**.
  나머지 비트 **[M]**: bit0 전원전압 저하, bit1 모터 과열, bit2 과전류, bit3 드라이버 과열,
  bit4 센서 이상, bit5 드라이버 이상, bit7 reserved.

## 값 변화 기반 판정에 넣으면 안 되는 필드

실패는 **두 방향**으로 난다:

1. **상시 변하는 필드가 하나라도 섞이면** 나머지 필드의 고착이 영구히 가려지고 게이트가 항상
   "신선"으로 뜬다.
2. **절대 변하지 않는 필드에 의존하면** 살아 있는 버스를 죽었다고 판정한다.

Ranger 토픽에서 해당하는 것 (1번 방향):

- **`/actuator_state`의 `motor.pulse_count`** — 0x251~8 byte[4..7]이고 매뉴얼 정의는
  *"The current position of the motor, whose unit is the number of pulses"* **[M]**, 즉 자유
  카운터가 아니라 **모터 위치**다. 그래서 두 방향 모두 부적합하다: 주행 중에는 매 프레임 바뀌어
  같은 도메인의 다른 필드 고착을 가리고, 정지 중에는 완전히 고정되어(실측: 정지 상태 8초간
  401 샘플 유니크 조합 1개) 생존 신호가 되지 못한다.
- **`header.stamp`** — 노드 발행 시점이라 항상 바뀐다. 도메인 비교에 넣으면 게이트가 영구히
  "신선"으로 뜬다.
- (정정) **0x211 byte[6..7]은 롤링 카운터가 아니다.** SDK 구조체가 이 자리를
  `reserved0 + count`로 선언하고 있으나(`agilex_protocol_v2.h:188`) 그것은 잘못된 해석이고,
  매뉴얼 Table 1과 실캡처가 일치하게 **error message의 상위 2바이트**다 **[M][R]**. 실캡처
  171,460회 프레임 간 증분이 전부 0이며, 8개 파일에서 취한 값도 byte[6]의 `0x01`(드라이버 상태),
  byte[7]의 `0x04`(RC 연결 상실)·`0x80`(비상정지)뿐이다. → 값 변화 판정에서 제외해도 무해하지만,
  이유는 "카운터라서"가 아니라 **"고장 비트이며 거의 상수라서"** 다.
- **(정정) 롤링 카운터는 존재한다 — 다만 SDK가 버린다** **[R]**. 위 항목에서 "이 펌웨어에는
  롤링 카운터가 존재하지 않는다"고 일반화했는데, 0x211 하나만 보고 내린 결론이라 틀렸다.
  **`0x231`(조명 상태)과 `0x241`(RC 상태)의 byte[7]은 프레임마다 정확히 +1인 롤링 카운터다**
  (실측 100%, n≈22,000). 그러나 SDK 파서가 이 바이트를 메시지 구조체로 옮기지 않는다
  — `RcStateFrame`에는 `count` 필드가 있으나 `RcStateMessage`에는 없고, `ranger_base`는 `rc_state`
  자체를 발행하지 않는다. → **상류에서는 여전히 쓸 수 없다.** 소비자가 쓸 수 있는 생존 신호는
  `feedback_count`이며, 섀시가 송신을 멈추면 둘은 같은 순간에 멈춘다. 갈리는 경우는 "섀시는
  보냈는데 우리가 못 받은" 구간뿐이고, 소비자 입장에서는 그것도 데이터 없음으로 같다.
  (이 카운터는 별도 용도가 있었다: 4.52초 버스 침묵이 **녹화 누락이 아니라 섀시가 실제로 송신을
  멈춘 것**임을 0x241 카운터가 단절 앞뒤로 +1인 것으로 판별했다. 누락이었다면 216이 건너뛰어야
  한다.)
- **`/odom.pose`** — 노드가 자체 적분하는 값이라 미세 변화가 누적될 수 있다. 오도메트리 도메인의
  생존 판정에는 `twist`(0x221 유래)를 쓰는 편이 근거가 명확하다.

2번 방향: **`/motion_state.motion_mode`는 정지 중 계속 0**이므로 생존 판정에 쓸 수 없다(변화가
없는 것이 정상, 실측 최대 고착 6,567초). 모션 도메인의 생존은 시스템 도메인 게이트에 위임하는
것이 맞다.

**예외가 생길 경우**: 상류가 "CAN 프레임 수신 카운트"를 노출하게 되면(미조치, 승인 대기)
그 필드는 **상시 변하는 것이 목적인 유일한 필드**이므로 위 1번 금지 목록의 예외로 명시해야
한다. 그 필드 하나만으로 생존을 판정하고, 다른 값 필드와 같은 도메인에 섞지 않는 편이 안전하다.

## `/odom`

`header.frame_id = odom`(파라미터 `odom_frame`), `child_frame_id = base_link`(`base_frame`).
`publish_odom_tf` 기본값 **false**이므로 노드는 TF를 쏘지 않는다.

`twist`는 섀시 보고값(0x221)에서 모드별로 재구성된다(`ranger_messenger.cpp:417-438`):

- DUAL_ACKERMAN: `linear.x`, `angular.z`(조향각과 휠베이스로 환산), `linear.y = 0`
- PARALLEL: `linear.x = v cos φ`, `linear.y = v sin φ`, `angular.z = 0`
- SPINNING: `linear = 0`, `angular.z` 만

`pose`는 노드가 자체 적분한 값이다(50 Hz). 섀시 오도메트리(0x311/0x312)와 별개이며 리셋 수단이 없다.

## 시뮬레이터로 검증할 때 주의 **[S]**

기준: `ranger_can_sim` `main` `3b30315`(2026-09-15 머지). 그 이전 버전이면 아래 **(해소)** 표시된
항목이 반대로 적용된다.

- **(해소) 0x111 수신 타임아웃 500ms가 구현됐다.** 명령이 500ms 이상 끊기면 정지 + 조향 중앙
  복귀로 실섀시와 같아졌다. 시나리오 러너(`scenario.simulate` / `drive_bus`)가 마지막 명령을
  20ms마다 재전송하므로, 시나리오를 쓰면 별도 `cmd_vel` 발행 주체 없이 로봇이 계속 움직인다.
  (이전 버전에서는 명령이 무기한 유지되어, "명령이 끝난 뒤 측정"하는 스크립트 결함이
  시뮬레이터를 통과하고 실기에서만 터졌다.)
- **(해소) 조향이 사다리꼴 프로파일로 바뀌었다.** `t(d) = d/3.26 + 0.064`, 0.21 rad 미만은 삼각
  프로파일. 실기 4점 측정(0.2/0.5/1.0/1.57 rad → 0.114/0.206/0.359/0.534초)을 재현한다.
  다만 모드 전환 게이팅을 조향 정착에서 유도하므로 **스핀 패턴 전환이 약 0.35초**가 되어,
  기존 관측 "~0.6초"와 상충한다. `1g` 측정(0x141 송신 → 같은 버스 0x281 속도가 임계를 넘는 시각)이
  나오면 갈린다. **세 숫자가 각각 다른 시점을 가리키므로 비교 대상을 맞춰야 한다**: 0.351초는
  조향 **완주**, 약 0.32초는 구동 **게이팅 해제**(정착 판정이 목표각 ±0.02 rad에서 먼저 서고,
  감속 구간의 마지막 0.02 rad이 약 0.028초), 0.57초는 `0x291` **전환 플래그** 지속이다.
  `1g`가 재는 것은 게이팅 해제이므로 0.32초 쪽과 비교해야 한다.
- 시뮬레이터의 `error_code` 비트 배치는 매뉴얼대로다(비상정지 `0x80`, RC 상실 `0x04`,
  드라이버 상태 `0x100`). **상류 테스트에는 여전히 byte[5]을 써야 한다** — SDK가 byte[4..5]만
  읽으므로 `0x100`은 `/system_state.error_code`에 도달하지 않는다(`error_code_full`에는 온다).
- 시뮬레이터 기본 제어모드는 standby이며, 노드가 붙어 0x421을 보내야 움직인다(정상 동작).
- **(해소) `WHEEL_RADIUS`가 실측 실효 구름 반경 85.3mm로 바뀌었다** (495.8 rpm/(m/s)에서 역산).
  공칭 90mm가 아니다.
- **(해소) BMS 송신 주기가 200ms로 바뀌었다** (실측 중위 201ms). 다만 실측은 중위 201 / p95 402의
  이봉에 가깝고 시뮬레이터는 고정 200ms이므로 **지터까지 같지는 않다** — 임계 여유를 잡을 때는
  실캡처 통계를 쓸 것. (`0x211`은 매뉴얼 20ms / 실측 20.9ms로 일치한다.)
- **(해소) BMS `current`에 양수(충전)를 주입할 수 있다**: `--battery-current 19.2`, 시나리오
  `{"battery": {"current": 19.2}}`, `chassis.set_battery_current()`. 기본값 -2.0(정지 대기 실측)은
  그대로다. 다만 **실캡처 재생 쪽이 전압·soc 동반 상승까지 실측**이라 더 충실하다:
  `122046 --start-at 2400 --duration 120`(+19 A 구간).
- **시뮬레이터는 기본적으로 구동 가속도가 무제한이다** — 속도가 0에서 목표로 한 틱에 뛴다.
  가속 램프(`max_linear_accel` / `max_angular_accel`)는 구현돼 있으나 **기본값이 `None`(옵트인)**
  이다. 지면 주행 동역학을 실측한 적이 없어 근거 없는 가속도를 기본값으로 박지 않겠다는 판단이고,
  근거가 생기기 전까지는 그게 맞다. 소비자 입장에서 걸리는 것:
  - 속도를 미분해 쓰면 시뮬레이터에서 **무한대에 가까운 가속도**를 본다.
  - **임계에 민감한 양이 시뮬레이터에서는 임계에 둔감해 보인다.** 모드 전환 지연을 예로 들면
    실기는 임계 0.001/0.05/0.1 m/s에서 0.017 / 0.374 / 0.892초로 갈리는데, 시뮬레이터는 세
    임계가 모두 같은 값이다(vcan0 실측 0.293 / 0.314초). **"임계를 안 적어도 된다"는 오답을
    시뮬레이터가 확인해 준다.**
  - 임계 민감도를 시뮬레이터에서 보고 싶으면 `RangerMini3Chassis(max_linear_accel=...)`로 켤 수
    있으나 **값 자체는 근거 없음**이다.
- **(해소) 조향 모터 rpm(0x255~8)이 `-723 × d(조향각)/dt`로 구현됐다** (정착하면 0). 이전에는
  구조적 0이라 그 필드에 의존하는 소비자가 시뮬레이터로 검증할 수 없었다. **다만 값이 맞아도
  소비자 검증은 실패할 수 있다** — 시뮬레이터는 CAN 프레임마다 정확한 값을 내는데 소비자가 ROS
  토픽을 미분하면 재발행 편향으로 -6%가 어긋난다(`/actuator_state` 절의 -723 / -669 / -608).
  **그때 원인이 시뮬레이터로 진단되기 쉽다.**
- **(해소) 조향각 포화가 구현됐다** — ackerman 내륜 0.698 / parallel 1.571에서 자르고 `0x221`도
  자른 값을 보고한다. Ackermann 차등 조향(`cot(외륜) - cot(내륜) = track/(wheelbase/2)`)도
  들어갔고, **명령 조향값은 내륜 각도로 해석**한다.
  **단, 노드를 경유해 테스트하면 포화의 출처를 구분할 수 없다**: 시뮬레이터 클램프 0.698과
  `ranger_base`의 `max_steer_angle_ackermann` 0.6981이 같은 수라 두 클램프가 겹친다. 섀시 포화만
  보려면 `0x111`을 직접 주입해야 한다.

## 미해결 / 후속

- **`feedback_count`의 "1 이상" 보장에 의존하는 소비자가 있다** (2026-09-14). `cona_comm`이
  `feedback_count == 0`을 "구버전 발행자"로 판정하고, 그 판정으로 `error_code_full` 같은 신규
  필드의 발행 여부를 가른다. 이 보장은 원래 **발행 게이트의 부수 효과**였고(첫 프레임 전에는
  발행하지 않으므로 처음 발행되는 값이 1) wrap 시 한 메시지에서 깨졌는데, 커밋 `27cb49f`로
  카운터가 스스로 0을 건너뛰게 해 게이트와 무관하게 성립한다. **게이트나 카운터를 손댈 때 이
  보장을 깨뜨리지 말 것** — 깨지면 소비자가 신버전 로봇을 구버전으로 오판한다.
- `soh` 상류 노출: `ranger_msgs` BMS 전용 메시지 신설이 합의됐으나 **`ranger_ros2` 수정은
  사용자 승인 대기**. `cona_comm` v1은 `soh` 없이 닫는 것으로 정리됨.
- 첫 CAN 프레임 수신 전 발행 억제(위 Critical 절): `ranger_base`에 수신 플래그 가드 추가.
  **사용자 승인 대기.** `soh` 작업과 같은 파일(`ranger_messenger.cpp` BMS 발행 블록)을 건드리므로
  함께 처리하는 것이 합리적이다.
- `percentage` 0~100 → 0~1 규약 준수 수정은 양쪽 동시 배포가 필요하므로, 착수 시 사전 통지.
