# Workflow - ranger_ros2

## TDD Policy

**Moderate.** Tests are encouraged but not blocking.

This is a real-time ROS 2 C++ driver whose primary interface is a CAN bus, so much of
the code cannot be meaningfully unit-tested without hardware. Apply judgment:

- **Do write tests** for self-contained, deterministic logic — motion-mode selection
  from a twist, steering-angle calculation, inner↔central angle conversion, parameter
  handling, and the kinematic models. These are pure functions of their inputs and are
  exactly where subtle regressions hide.
- **Do not block** implementation on coverage for hardware-dependent paths (`ugv_sdk`
  calls, CAN transport, chassis feedback). Verify those on the robot or against
  `ranger_can_sim`.

Note that the repository currently has **no test suite at all**. Adding one is a
worthwhile track in its own right; until then, "moderate TDD" means write tests where a
harness exists or is cheap to add, and rely on on-robot verification elsewhere.

## Commit Strategy

**The developer commits their own work.** Do not create commits automatically.

Implementation work should be left staged or unstaged in the working tree for the
developer to review and commit themselves. This applies to Conductor track
implementation as well: complete the task, report what changed, and stop — the commit is
the developer's call.

When the developer does ask for a commit to be written, follow the convention already
dominant in this repository's history:

- `feat:` — new feature or behavior
- `fix:` — bug fix
- `refactor:` — restructuring with no behavior change
- `perf:` — performance improvement
- `docs:` — documentation only
- `build:` / `chore:` — build system, tooling, housekeeping

Scope with the package name where useful, e.g.
`fix(ranger_base): add hysteresis and min-dwell to motion-mode switching`.
One logical change per commit.

## Code Review

**Optional.** Self-review is acceptable and PRs are not mandated for every change.

Review is encouraged for changes touching motion-mode selection, the CAN command path,
or the per-variant kinematic parameters, since those affect chassis safety and can
damage hardware or unseat an operator. The repository does use PRs when it makes sense
(see the merge of PR #6).

## Verification Checkpoints

**After each phase.** A manual verification checkpoint is required when a phase of a
track completes. For this driver, verification means:

1. **Builds clean** — `colcon build --packages-select ranger_msgs ranger_base` succeeds
   with no new warnings.
2. **Node launches** — the appropriate `ranger*.launch.py` starts, and `ros2 topic list`
   shows the expected topics (`/system_state`, `/motion_state`, `/actuator_state`,
   `odom`, `/battery_state`).
3. **Behavior is checked** — drive the robot (or `ranger_can_sim`) and confirm the
   change does what it claims. For anything touching mode selection, this specifically
   means watching `/motion_state` while sweeping `/cmd_vel` across the relevant decision
   boundary and confirming the mode does **not** chatter and the motion has no
   perceptible jolt.
4. **No regression in the other modes** — a change aimed at one motion mode must not
   alter behavior in the others.

Do not proceed to the next phase until the checkpoint passes. If verification requires
hardware that is not currently available, say so explicitly and pause rather than
marking the phase complete.

## Task Lifecycle

1. **Plan** — task defined in a track plan (`/conductor:new-track`).
2. **Implement** — make the change, following `product-guidelines.md` and the C++ style
   guide. Mark the task `[~]` while in progress.
3. **Build** — confirm the affected packages compile.
4. **Verify** — at each phase boundary, run the verification checklist above.
5. **Complete** — mark the task `[x]`. Leave the changes uncommitted for the developer.

## Build Notes

- Build only what changed: `colcon build --packages-select ranger_msgs ranger_base`.
- `ranger_base` depends on `ranger_msgs`; if a `.msg` changes, rebuild both.
- `--symlink-install` and a previously non-symlink build directory conflict. If
  `ranger_msgs` fails with *"failed to create symbolic link ... Is a directory"*, remove
  `build/ranger_msgs` and rebuild.
- Re-enable the commented-out `ament_lint_auto` block in `ranger_base/CMakeLists.txt`
  so linting runs as part of the build.
