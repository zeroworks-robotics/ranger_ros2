# Python Style Guide - ranger_ros2

Python in this repository is used **only for ROS 2 launch files**
(`ranger_base/launch/*.launch.py`, `ranger_bringup/launch/*.launch.py`). There is no
Python node code. Scope the conventions accordingly.

## Baseline

**PEP 8** with 4-space indentation and an 80–99 column limit. Follow the ROS 2 launch
idioms below where they conflict with generic Python advice.

## Launch File Structure

Every launch file exposes a `generate_launch_description()` returning a
`LaunchDescription`:

```python
from launch import LaunchDescription
from launch.actions import DeclareLaunchArgument
from launch.substitutions import LaunchConfiguration
from launch_ros.actions import Node


def generate_launch_description():
    port_name_arg = DeclareLaunchArgument('port_name', default_value='can0')
    robot_model_arg = DeclareLaunchArgument('robot_model', default_value='ranger')

    ranger_base_node = Node(
        package='ranger_base',
        executable='ranger_base_node',
        name='ranger_base_node',
        output='screen',
        parameters=[{
            'port_name': LaunchConfiguration('port_name'),
            'robot_model': LaunchConfiguration('robot_model'),
        }],
    )

    return LaunchDescription([
        port_name_arg,
        robot_model_arg,
        ranger_base_node,
    ])
```

## Conventions

- **Declare arguments, don't hardcode.** Anything an operator might reasonably change —
  `port_name`, `robot_model`, frames, topic names — is a `DeclareLaunchArgument` with a
  sensible default, not a literal buried in the `Node`.
- **Defaults must match the node.** A launch default must agree with the C++
  `declare_parameter` default. A silent disagreement between the two is a real source of
  "it behaves differently under launch" bugs.
- **One variant per launch file.** The existing split
  (`ranger.launch.py`, `ranger_mini_v1.launch.py`, …) is intentional; keep it rather
  than adding a variant switch inside one file.
- **Name the node explicitly** with `name=`, so it is addressable and its parameters are
  reachable by a stable fully-qualified name.
- **Quotes:** single quotes, matching the existing launch files.
- **Imports:** standard library, then `launch*`, then `launch_ros`. One import per line.
- **Trailing commas** in multi-line lists and dicts, so diffs stay one line per change.

## Parameters

- Parameter names are `snake_case` and identical to the C++ member without its trailing
  underscore — `cmd_deadzone_` ↔ `'cmd_deadzone'`.
- Pass numeric parameters as the correct Python type — `0.6`, not `'0.6'`. A string
  where a double is expected fails at runtime, not at launch-file parse time.
- Document units in a comment when the name does not carry them:
  ```python
  'mode_switch_min_dwell': 0.6,   # s
  'cmd_deadzone': 0.01,           # m/s, rad/s
  ```

## What Not to Do

- No business logic in launch files. They wire nodes together; decisions belong in C++.
- No `os.system` / `subprocess` calls to bring up CAN — that is what the bash scripts in
  `ranger_bringup/scripts/` are for.
- No unused imports; `ament_lint` will flag them once re-enabled.
