# Product Guidelines - ranger_ros2

## Voice and Tone

**Professional and technical.** Documentation, code comments, and ROS parameter
descriptions are precise and engineering-focused.

- Use exact terminology: frames, topics, CAN IDs, motion-mode names as they appear in
  `ranger_msgs/msg/MotionState.msg`.
- State units explicitly — linear velocity in m/s, angular velocity in rad/s, steering
  angles in radians, dwell times in seconds.
- State assumptions rather than implying them. Where a comment explains *why* a
  threshold or guard exists (e.g. the ~0.6 s steering reconfiguration cost), keep that
  reasoning in the code; it is the most valuable part of the comment.
- Prefer explaining rationale over restating the code. The existing comment style in
  `ranger_base/src/ranger_messenger.cpp` is the reference.

## Design Principles

1. **Smooth operator experience** — mode transitions and velocity changes must not
   produce a perceptible jolt. Anti-chatter measures are first-class design concerns,
   not afterthoughts:
   - a **deadzone** so command noise near zero cannot trigger a mode change,
   - **hysteresis** on decision boundaries so a value lingering at the threshold cannot
     oscillate,
   - a **minimum dwell** so a brief excursion across a boundary cannot thrash the
     chassis,
   - **holding the current mode** when nothing is commanded, rather than snapping back
     to a default.

   When adding any new mode-affecting behavior, ask what happens if the input hovers
   exactly at the boundary. If the answer is "it flips back and forth," the design is
   not finished.

## Additional Standards

- **Units:** distances in meters, linear velocity in m/s, angular velocity in rad/s,
  angles in radians, times in seconds — unless explicitly noted otherwise.
- **Frames:** be explicit about source and target TF frames; never assume a frame.
  `odom_frame` and `base_frame` are parameters, not constants.
- **Defaults:** every tunable must have a safe default that matches the header
  initialization, so the node runs correctly without a fully-specified launch file.
- **Mode-switch cost:** treat `robot_->SetMotionMode()` as expensive. Never call it
  unconditionally in a per-message callback; it must be gated on an actual change.
- **Variant awareness:** behavior that differs between Ranger, Mini V1, Mini V2, and
  Mini V3 must be explicitly guarded on `robot_type_`, not left implicit.
