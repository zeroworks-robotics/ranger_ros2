## Overview

A small, self-contained feature: one subscriber, one callback, one SDK call. The plan is
correspondingly short.

The one thing that could waste real effort is building the whole path and only then
discovering the chassis has no controllable lights — the SDK's own
`DisableLightControl()` stub hints that some Ranger variants don't. Phase 1 therefore
answers that question directly, with a throwaway call, before any interface work happens.

**On testing:** per `workflow.md` (moderate TDD), this is a hardware path with no
testable pure logic beyond "bool maps to enum", and the repository has no test harness.
Verification is on-robot.

## Phase 2: Implement the Topic

Add the subscriber and callback, following the patterns already in the driver.

### Tasks

- [ ] Task 2.1: Declare `LightControlCallback(std_msgs::msg::Bool::SharedPtr msg)` and a
      `light_control_sub_` member in `ranger_messenger.hpp`, placed with the other
      callbacks and subscription members. Add a `light_on_` member to track last
      commanded state, initialized to represent "nothing commanded yet".
- [ ] Task 2.2: Create the subscription on `/light_control` in `SetupSubscription()`,
      alongside `motion_cmd_sub_` and `control_mode_sub_`.
- [ ] Task 2.3: Implement the callback — map `true` → `SetLightCommand(CONST_ON, 0,
      CONST_ON, 0)` and `false` → `SetLightCommand(CONST_OFF, 0, CONST_OFF, 0)`. Gate on
      a change in `light_on_` so a repeated value issues no CAN traffic, mirroring how
      `commanded_motion_mode_` gates `SetMotionMode()`. Log only on an actual change.
- [ ] Task 2.4: Remove the throwaway call from Task 1.2.
