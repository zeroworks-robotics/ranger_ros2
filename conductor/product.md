# Product Definition - ranger_ros2

## Overview

**ranger_ros2** is a ROS 2 driver for AgileX / Weston Robot **Ranger** mobile robot
bases. It exposes the chassis over a standard ROS 2 interface: it accepts velocity
commands, drives the chassis over CAN via `ugv_sdk`, and publishes odometry, system
state, motion state, actuator state, and battery state back to ROS.

## Description

The repository provides three ROS 2 packages:

| Package | Role |
| --- | --- |
| `ranger_base` | The driver node. Translates `/cmd_vel` into CAN motion commands, selects the chassis motion mode, integrates odometry, and republishes chassis feedback. |
| `ranger_msgs` | Message definitions for the Ranger-specific state topics (`MotionState`, `SystemState`, `ActuatorState`, `DriverState`, `MotorState`, `ActuatorStateArray`). |
| `ranger_bringup` | Launch files for bringing up a robot, plus the CAN-to-USB setup scripts. |

Supported chassis variants: **Ranger**, **Ranger Mini V1**, **Ranger Mini V2**, and
**Ranger Mini V3**. Each variant has its own kinematic parameters (track, wheelbase,
maximum steering angles, speed limits) selected by the `robot_model` parameter.

The defining behavior of the driver is **motion-mode selection**. A Ranger chassis is
four-wheel independent-steer and exposes several distinct motion modes:

- `DUAL_ACKERMAN` — normal driving; front and rear steer opposite, follows an arc.
- `PARALLEL` — all wheels steer the same way; the robot crabs diagonally.
- `SPINNING` — turn in place.
- `SIDE_SLIP` — pure lateral translation (Ranger Mini V1).
- `PARKING` — chassis halted (Ranger Mini V2/V3).

The driver derives the appropriate mode from the commanded twist on `/cmd_vel`, so the
same rules apply to every command source — joystick teleop, `cmd_vel_manager`, or an
autonomous navigation stack. A real mode switch costs the chassis roughly 0.6 s of
steering reconfiguration during which it ignores speed commands, so mode selection is
deliberately damped: a command deadzone, hysteresis on the ackermann↔spinning boundary,
and a minimum dwell time between switches.

## Problem Statement

A Ranger chassis speaks CAN, not ROS. Software teams need a ROS 2 interface that hides
the CAN protocol and, critically, decides **which motion mode the chassis should be in**
for a given velocity command.

That decision is the hard part. Mode switching is physically expensive and
operator-visible: the chassis stops responding to speed while it reconfigures its
steering, so a naive threshold on velocity makes the robot stutter whenever a command
lingers near a decision boundary — a deceleration tail, joystick jitter, or a navigation
stack easing into a turn. The driver has to pick the right mode without thrashing, and
it has to do so identically whether a human or a planner is driving.

## Target Users

**Internal robotics team.** Zeroworks engineers who integrate and operate the robot —
the people writing navigation stacks, teleop, and bringup against this driver, and who
debug chassis behavior in the field.

## Key Goals

1. **Safe, reliable chassis control** — never command the chassis into a damaging or
   surprising state. Respect parking mode, control-mode gating, and the per-variant
   speed and steering limits.
2. **Predictable motion-mode switching** — correct, chatter-free selection between
   dual-ackerman, parallel, spinning, and side-slip, driven purely by the commanded
   twist so behavior is reproducible and source-independent.
3. **Smooth, non-jarring movement across mode changes** — the operator should not feel
   a jolt when the mode changes. Transitions must be damped and infrequent enough that
   motion reads as continuous.
